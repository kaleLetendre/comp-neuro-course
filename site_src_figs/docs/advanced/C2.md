## Lesson spec

**Goal:** Name which variable each loop minimizes energy over — activity in the inner loop, weights in the outer — and why the weight update assumes the inner loop already reached a fixed point. Turns "settle 100 iterations, then update" from an arbitrary hyperparameter into a schedule with a reason, and connects it to why carrying state across inputs and running Adam mid-rollout are architectural decisions with real failure modes.

??? note "Scope — what the lesson covers"

    - Two loops, one energy: inner descends activity (fast, per input), outer descends weights (slow, per batch); what each holds fixed
    - Why weight updates use the converged error, and what breaks in the gradient when weights update from a partially settled state
    - Batch/offline schedule vs a deployed network with no "done" — where the inner loop's stopping condition comes from when input never stops
    - State persistence as a choice: when carrying settled activity forward speeds re-settling, and when it traps the network in a stale basin
    - Why a momentum-based optimizer's state assumes a stationary training distribution, which a live rollout is not
    - Not covered: precision-weighted errors (C3), clamping patterns (C5), the backprop-equivalence proof (C6)

**You should be able to answer:**
1. In the CartPole rollout, which loop runs 100 iterations, and which variable does it hold fixed while doing so?
2. If weights update after only 10 of the 100 settling iterations, what specifically is wrong with the gradient computed?
3. Name one condition where carrying settled state into the next input's inner loop speeds convergence, and one where it produces a wrong answer.
4. Why does SGD tolerate a live rollout's shifting distribution better than Adam's carried-over moment estimates?
5. In a deployed network that never stops receiving input, what replaces the epoch boundary as the trigger to update weights?

**Project tie-in:** Explains the Step 2b finding that SGD works but carried-over Adam state blows up in `online_rollout.py`, and why the 100-iteration inference settle in `train_cartpole.py` is not an arbitrary constant.

**Done when:** You states the fixed-prediction assumption the outer loop relies on, without notes, and names the specific Step 2b consequence of violating it.

=== "Piece 1 — Fixed point vs partial settle"

    **Type:** derivation · **Time:** 60–75 min

    **Learning goals**
    - Write the inner-loop (activity) update and outer-loop (weight) gradient for a small PC chain from its energy function.
    - Derive the inner loop's analytic fixed point and show the weight gradient is only correct once the inner loop has reached it.
    - Quantify, with actual numbers, how wrong the weight gradient is after 1, 3, 5, and 10 inner-loop ticks instead of running to convergence.
    - State in one sentence what assumption the outer loop is making about the inner loop's state.

    **Task**

    Use this 3-node PC chain: `x0` (input, clamped to 1) → `x1` (hidden, free) → `x2` (target, clamped to 1). Predictions run top-down: `x1` predicts `x0` through weight `w0`, and `x2` predicts `x1` through weight `w1`. Errors: `e0 = x0 - w0*x1`, `e1 = x1 - w1*x2`. Energy: `F(x1) = 0.5*e0^2 + 0.5*e1^2`. Fix `w0 = 2`, `w1 = 1`, inner-loop step size `alpha = 0.1`, and start `x1` at 0.

    1. Derive `dF/dx1` symbolically, then write the inner-loop update rule `x1 ← x1 - alpha * dF/dx1` in the form `x1_{t+1} = a*x1_t + b` (find `a` and `b` as numbers).
    2. Solve for the analytic fixed point `x1*` two ways: (a) setting `dF/dx1 = 0` directly, (b) setting `x1_{t+1} = x1_t` in your recurrence from step 1. Confirm they agree.
    3. Derive `dF/dw0` and `dF/dw1` as functions of `x1` (these are the outer-loop gradients).
    4. Hand-run the inner-loop recurrence for `t = 0, 1, 2, 3, 5, 10` (tick-by-tick — show each `x1_t`), then evaluate `dF/dw0` and `dF/dw1` at each tick and at the true fixed point. Build a table: tick | `x1_t` | `dF/dw0` | `dF/dw1` | error vs. fixed-point gradient (absolute and %).
    5. In 2–3 sentences: what is qualitatively different about the `dF/dw0` error at `t=1` versus `t=10`, and what does that say about updating weights before the inner loop has settled?

    **Deliverable:** handwritten or typed derivation + the numeric table from step 4, plus the 2–3 sentence answer to step 5.

    ??? info "Rubric — how this is marked"

        | Band | Criteria |
        |---|---|
        | Strong | Correct symbolic `dF/dx1`, correct recurrence coefficients, both fixed-point derivations agree, table numerically correct within rounding, and the written answer names that the early-tick gradient for `w0` has the *wrong sign*, not just "less accurate." |
        | Adequate | Symbolic derivation and fixed point correct; table has minor arithmetic slips but the right shape (error shrinking with more ticks); written answer says the gradient is "biased" or "wrong" early on without noting the sign flip. |
        | Not yet | Fixed point wrong, or table gradients computed from the wrong `x1` values, or the written answer only restates "more iterations is more accurate" without engaging with what the gradient formula is measuring. |

=== "Piece 2 — Sweeping the inner-loop budget"

    **Type:** simulation · **Time:** 90–120 min

    **Learning goals**
    - Build a minimal PC network with an explicit inner (activity) loop and outer (weight) loop in PyTorch or numpy.
    - Empirically confirm Piece 1's claim: too few inner-loop steps produce a systematically worse outer loop, and locate where the returns from more inner steps flatten out.
    - Observe, on a non-stationary data stream, that a momentum/second-moment optimizer's carried-over state fails in a way plain SGD doesn't — the mechanism behind the Step 2b finding.

    **Task**

    Part A (required): implement a 1-hidden-layer PC network (2 free/clamped nodes is enough — reuse the `x0/x1/x2` structure from Piece 1 or extend it to a small vector) trained on a synthetic linear or mildly nonlinear regression task (e.g. `y = 2*x + 0.5*sin(x) + noise`, ~200 samples). For each of `inner_steps ∈ {1, 5, 20, 100}`: run the outer loop for a fixed number of weight updates (e.g. 300), with the inner loop settling activity for exactly `inner_steps` gradient steps before each weight update. Log final held-out MSE for each `inner_steps` value. Plot or tabulate MSE vs. `inner_steps`.

    Part B (optional but recommended): take the `inner_steps=100` (well-settled) network and continue training on a stream where the input distribution shifts partway through (e.g. `x` drawn from `N(0,1)` for the first half of updates, `N(4,1)` for the second half — no i.i.d. shuffling, sequential). Compare plain SGD against Adam on this stream: log the per-step weight-update magnitude for both optimizers across the shift point and note what Adam's moment estimates do right after the shift.

    **Deliverable:** one script (<~100 lines, self-contained, synthetic data, no repo imports), its output (MSE table for Part A; the update-magnitude comparison plot or table for Part B if attempted), and 3–5 sentences interpreting the inner_steps=1 result in light of Piece 1's sign-flip finding.

    ??? info "Rubric — how this is marked"

        | Band | Criteria |
        |---|---|
        | Strong | Script runs standalone, correctly separates inner-loop (activity, no weight grad) from outer-loop (weight update using settled activity, no activity grad) updates, MSE table shows monotonic-ish improvement with more inner steps that visibly flattens by 20–100, and the interpretation explicitly ties `inner_steps=1` degradation back to the sign/magnitude error from Piece 1 (not just "it's worse"). Bonus credit, not required, for a correct and interpreted Part B. |
        | Adequate | Script runs and produces the expected qualitative pattern (fewer inner steps → worse MSE), but the inner/outer separation is fuzzy (e.g. gradients leak between them) or the interpretation is generic rather than connected to Piece 1. |
        | Not yet | Script conflates the two loops (e.g. one gradient step does both activity and weight updates simultaneously), doesn't sweep `inner_steps` as a controlled variable, or the MSE pattern is flat/reversed with no attempt to explain why. |

=== "Piece 3 — Guided reading: Dayan & Abbott, ch. 10 (Density Estimation)"

    **Source chosen:** D&A ch. 10, for the E-step/M-step parallel to the inference/learning split (chosen over the Millidge review because the lesson's core claim — two nested loops, one energy, each holding the other fixed — has an exact structural match in EM, and D&A ch. 10 makes that pairing explicit rather than as one variant among many).

    **Type:** guided reading · **Time:** 60–90 min

    **Learning goals**
    - Map EM's E-step and M-step onto PC's inner (activity) and outer (weight) loop, term for term.
    - Identify what plays the role of the "hidden variable" in each formalism and why both algorithms hold one set of variables fixed while optimizing the other.
    - Articulate why EM's convergence guarantee (each step doesn't increase the negative log-likelihood) depends on the E-step being run to completion, and connect that to Piece 1's fixed-point requirement.

    **Task**

    Read D&A ch. 10, focusing on the sections that set up the EM algorithm for a mixture model (skim the specific mixture-of-Gaussians algebra if it's slow going — the structural argument is what matters here, not the mixture-model details). While reading, fill in this correspondence table from memory afterward, without looking back at the chapter or at Piece 1:

    | | E-step / M-step (D&A ch.10) | Inner/outer loop (this project) |
    |---|---|---|
    | What varies in this step | | |
    | What's held fixed | | |
    | What quantity is optimized (name the objective) | | |
    | Stopping condition for this step | | |

    Then write 3–5 sentences: EM alternates "compute the posterior over hidden variables given current parameters" and "update parameters given that posterior." Which of PC's two loops is which, and where does the *guarantee* that EM's overall objective doesn't get worse depend on the E-step being complete rather than partial (tie this to Piece 1's numbers if useful)?

    **Deliverable:** the filled correspondence table plus the 3–5 sentence answer.

    ??? info "Rubric — how this is marked"

        | Band | Criteria |
        |---|---|
        | Strong | Table correctly maps E-step↔inner loop (activity/posterior, held-fixed=parameters) and M-step↔outer loop (weights/parameters, held-fixed=posterior/activity); the written answer correctly identifies that EM's monotonic-improvement guarantee is a property of the *exact* posterior — a partial E-step breaks the bound the same way a partially settled inner loop makes the outer-loop gradient in Piece 1 wrong. |
        | Adequate | Table mostly correct but with one swapped row (e.g. confusing which step holds which variable fixed); written answer gestures at the parallel without stating specifically what breaks with a partial E-step. |
        | Not yet | Table maps E-step and M-step to the wrong loops, or the written answer treats EM and PC as merely "similar" without naming which variable is optimized/fixed in each. |

=== "Piece 4 — Written defence: what triggers a weight update when input never stops"

    **Type:** written defence · **Time:** 45–60 min · **Length:** 300–600 words

    **Learning goals**
    - Explain, without notes, why SGD tolerates a live rollout's shifting distribution better than Adam's carried moment estimates.
    - Propose and defend a concrete replacement for "epoch boundary" as the outer-loop trigger in a network with no natural stopping point — this is an open design question for Steps 3–5, not a settled answer, and should be argued as such.

    **Task**

    Write 300–600 words answering, as one connected argument (not five disconnected paragraphs):

    1. Why does plain SGD tolerate CartPole's live, shifting rollout distribution better than Adam, given what Adam's optimizer state actually tracks?
    2. Propose one concrete, specific trigger for "now update the weights" in a network that receives input continuously and has no epoch boundary. It must be checkable from quantities the network already has access to at runtime (e.g. settling residual, error magnitude, elapsed steps, a stress-like signal) — not "whenever it seems ready."
    3. State one failure mode of your proposed trigger and how you'd detect it happening.

    This is explicitly a proposal, not a lookup — there is no single correct trigger. The defence is judged on whether the reasoning connects correctly to the settling/gradient mechanics from Pieces 1–2, and whether the proposal is concrete enough to falsify.

    **Deliverable:** 300–600 word written answer.

    ??? info "Rubric — how this is marked"

        | Band | Criteria |
        |---|---|
        | Strong | Correctly explains Adam's failure via its carried second-moment estimate being calibrated to a distribution that no longer holds (not just "Adam is more complex"); proposes a specific, checkable trigger (e.g. "update when the inner loop's residual error drops below a threshold and stays there for k ticks" or "update every N environment steps, chosen so N ≫ typical settling time"); names a real failure mode of that specific trigger (e.g. a threshold-based trigger firing on a transient lull) and a way to detect it (e.g. tracking trigger frequency and flagging if it fires too often). |
        | Adequate | Correct SGD/Adam explanation; trigger proposal is plausible but vague enough to be hard to falsify (e.g. "update periodically" with no stated relationship to settling time) or the failure mode named doesn't actually apply to the proposed trigger. |
        | Not yet | Adam/SGD explanation is generic ("Adam overfits") without referencing carried moment state; no concrete trigger proposed, or the proposal restates "when the epoch ends" without addressing that there is no epoch. |

## Completion bar

Coursework is complete when: Piece 1's derivation and numeric table are correct (or corrected via the hint ladder) and you can state, without notes, that the outer-loop weight gradient is only valid once the inner loop has reached its fixed point; Piece 2's simulation runs standalone and shows the expected inner_steps pattern; Piece 3's correspondence table correctly pairs E-step/M-step with inner/outer loop; and Piece 4's written defence proposes a concrete, falsifiable weight-update trigger and correctly explains the SGD/Adam mechanism. You should be able to say, unprompted, what specifically goes wrong with the Step 2b gradient/optimizer if either the inner-loop settling budget or the weight-update schedule is treated as an arbitrary hyperparameter rather than a consequence of the fixed-point assumption.
